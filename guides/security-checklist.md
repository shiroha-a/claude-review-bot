# セキュリティチェックリスト（レンズ B: データフローと信頼境界）

セキュリティレビューは「怪しい API を grep する」作業ではなく、**source から sink まで入力を追う**作業。
`eval` があっても引数が定数なら脆弱性ではないし、`execute(query)` が無害に見えても query が 10 行上で連結されていれば脆弱性。
だから手順はこうなる:

1. 地図づくりで挙げた **エントリポイント**ごとに、入ってくる値を列挙する（パス、クエリ、ヘッダ、ボディ、Cookie、ファイル名、環境変数、DB から読んだ値も「過去に外部から来た値」）
2. 各値について、**どこで検証・エスケープ・型変換されるか**、されないまま **どのシンクに届くか** を追う。間の関数に入って読む
3. シンクに届いた形（文字列結合か、パラメータか、エスケープ済みか）で判定する
4. **認可**は別軸で、「このハンドラに来た主体が、この対象に対してこの操作をしていいか」を全ハンドラで確認する

## 信頼境界の確認

- どの層で認証されるか（ミドルウェア？各ハンドラ？）。新しいハンドラ・ルートがその層を **通っているか** を実際にルーティング定義で確認する（内部用・ヘルスチェック・デバッグ・Webhook 用のルートが素通りになりがち）
- 「内部からしか呼ばれない」前提の関数が、新しい経路で外部入力を受けるようになっていないか
- 他サービス・DB・キュー・ファイルから読んだ値を「信頼できる」と扱っていないか（上流が汚染されれば下流も汚染される: 保存型 XSS、保存型インジェクション）
- 管理者機能・デバッグエンドポイント・feature flag の裏の機能が本番で露出していないか
- CLAUDE.md / REVIEW.md / SECURITY.md に「この層で検証済み」「受容済みリスク」の記述があれば、それは **根拠つきで** 候補から外す

## インジェクション（source → sink）

**SQL / NoSQL / ORM**

- 文字列連結・フォーマット（f-string、`+`、`format`、`sprintf`、テンプレートリテラル）で組んだクエリ。ORM でも `raw()`、`extra()`、`whereRaw`、`$where`、`Sequelize.literal`、`gorm.Exec(fmt.Sprintf(...))` 等
- プレースホルダを使っているが、**テーブル名・カラム名・ORDER BY・LIMIT** を連結している（ホワイトリストで検証されているか）
- NoSQL: クエリオブジェクトにユーザー入力のオブジェクトをそのまま入れる（`{ username: req.body.username }` で `{"$ne": null}` が渡る）
- LIKE のワイルドカード（`%`、`_`）を未エスケープで通す（DoS・情報漏えい）

**コマンド**

- `exec`、`system`、`popen`、`subprocess` with `shell=True`、`child_process.exec`、`os/exec` でシェル経由（`sh -c`）、バッククォート
- 引数配列で渡していても、引数の先頭が `-` で始まるとオプションとして解釈される（`--output=/etc/passwd`）。`--` で区切っているか
- 環境変数・ファイル名・URL をコマンドに含める

**パス**

- `../`、絶対パス、`~`、NUL バイト、URL エンコード（`%2e%2e%2f`）、バックスラッシュ（Windows）、Unicode 正規化後の `..`
- `path.join(base, userInput)` は **防御にならない**（絶対パスで base が消える、`..` が残る）。`filepath.Clean` / `path.normalize` 後に base で始まるかを確認しているか。シンボリックリンク追従
- アーカイブ展開（zip slip）、アップロードファイル名、テンプレート名、ログファイル名、ロケール名

**テンプレート / HTML / スクリプト**

- サーバサイドテンプレートにユーザー入力を **テンプレート文字列として** 渡す（SSTI）
- 自動エスケープを無効化する箇所（`| safe`、`Markup`、`dangerouslySetInnerHTML`、`v-html`、`innerHTML`、`template.HTML`、`{!! !!}`）。渡る値はサニタイズ済みか
- JS 文脈・属性文脈・URL 文脈（`href="javascript:"`、`onclick`）へのエスケープ漏れ。HTML エスケープは文脈を間違えると無効
- JSON を `<script>` に埋め込むときの `</script>` エスケープ
- Markdown レンダラの HTML 許可設定

**その他のシンク**

- LDAP、XPath、XML（XXE: 外部エンティティ有効のパーサ）、正規表現（入力をパターンにする）、ヘッダ（CRLF インジェクション）、ログ（改行）、メール（ヘッダインジェクション）、リダイレクト先、`eval`/`Function`/`pickle`/`yaml.load`/`unserialize`/`ObjectInputStream`（デシリアライズ）
- フォーマット文字列をユーザー入力にする（`printf(user)`、Python の `.format(**user)` で属性アクセス）

## 認証・認可

**認証**

- パスワード・トークンの比較が定数時間か（`==` でなく `hmac.compare_digest` / `crypto.timingSafeEqual` / `subtle.ConstantTimeCompare`）
- セッション ID・トークン・リセットコード・招待コードの生成に暗号学的乱数を使っているか（`math/rand`、`random`、`Math.random` は不可）。十分な長さか
- JWT: `alg` を検証側で固定しているか（`none`、RS→HS 混同）、署名検証なしの `decode` を使っていないか、`exp`/`nbf`/`aud`/`iss` を検証しているか、鍵の取り回し
- パスワードハッシュ: bcrypt/scrypt/argon2 か（MD5/SHA-1/無塩 SHA-256 は不可）
- ログイン・リセット・OTP にレート制限・ロックアウトがあるか
- セッション: ログイン後に ID を再生成しているか（固定化）、ログアウト・パスワード変更で無効化されるか、Cookie に `HttpOnly`/`Secure`/`SameSite`
- 認証失敗の情報（ユーザー存在の有無が分かる応答・時間差）

**認可（最も見逃されやすい）**

- **オブジェクト単位の認可（IDOR/BOLA）**: `GET /orders/:id` で、その order が **リクエスト主体のものか** を確認しているか。`WHERE id = ?` だけで `AND user_id = ?` がないクエリを探す。更新・削除・一覧・エクスポート・ファイル取得すべてで
- **機能単位の認可**: 管理者機能・他テナントのデータ・内部 API に、ロール確認があるか。確認はミドルウェアか、ハンドラ内で忘れうるか
- **マスアサインメント**: リクエストボディを構造体・モデルにそのままバインドし、`role`、`is_admin`、`owner_id`、`price`、`verified` などを書き換えられる
- 認可の判定が **クライアント由来の値**（ヘッダの user id、ボディの role、JWT の未検証クレーム）に基づいている
- 認可チェックとデータ取得の間で対象が変わりうる（ID で確認して別の ID で取得）
- 一覧 API のフィルタ・検索・ソート引数で他人のデータが条件に入れられる
- GraphQL / 一括 API のネストで、個別取得では守られている認可が抜ける
- 多段階フロー（ウィザード、決済）で前のステップの完了を確認せず後のステップを直接叩ける

## 秘密情報と暗号

- ハードコードされた鍵・パスワード・トークン・接続文字列（テスト用でも本番に残る）。git 履歴に残る
- 秘密情報がログ・エラーメッセージ・URL クエリ・リファラ・クラッシュレポート・クライアントへのレスポンスに出る
- 暗号: ECB モード、固定 IV/nonce、鍵の再利用、独自暗号、`MD5`/`SHA1` の署名用途、暗号化のみで認証なし（AES-CBC without MAC → パディングオラクル）、乱数の種が時刻
- TLS 検証の無効化（`InsecureSkipVerify`、`verify=False`、`rejectUnauthorized: false`、`NODE_TLS_REJECT_UNAUTHORIZED=0`）
- 署名・HMAC の検証で、比較が定数時間か、アルゴリズム・鍵 ID が入力で選べないか
- 秘密情報をメモリ・一時ファイル・環境変数（子プロセスに継承）に置く範囲

## サーバサイドリクエスト（SSRF）とリダイレクト

- ユーザー入力の URL・ホスト・ポートで HTTP 取得・接続する（Webhook URL、画像取得、インポート、プロキシ、PDF レンダラ、ヘルスチェック）
- 対策の確認: スキーム制限、プライベート IP / リンクローカル（169.254.169.254 = クラウドメタデータ）/ localhost / `0.0.0.0` / IPv6 / 10 進 IP の拒否、**リダイレクト追従後** の再検証、DNS リバインディング
- オープンリダイレクト: `next`、`redirect_to`、`return_url` が相対パスに限定されているか（`//evil.com`、`/\evil.com`、`https:evil.com` をすり抜けないか）

## 入力の検証とアップロード

- サイズ上限（ボディ、ファイル、配列長、文字列長、JSON の深さ、ヘッダ数・長さ）
- Content-Type / 拡張子 / マジックバイトの整合、ファイル名のサニタイズ、保存先がドキュメントルート外か、実行権限
- 数値の範囲（負の数量、負の金額、0 件、巨大ページサイズ）
- 列挙値・ID の形式検証（検証せずに文字列として連結する箇所がないか）
- 複数の同名パラメータ、配列/オブジェクトの型違い（`?id=1&id=2`、`id[]=`）
- **プロトタイプ汚染**（JS）: `__proto__`、`constructor.prototype` をキーに持つオブジェクトの再帰マージ・`Object.assign`
- デシリアライズ: 型が指定できる形式（pickle、Java シリアライズ、YAML の `!!python`、PHP `unserialize`、.NET `TypeNameHandling`）で外部入力を読む

## Web 固有

- CSRF: 状態変更を GET で行う、トークン未検証、`SameSite` なし Cookie 認証の POST
- CORS: `Access-Control-Allow-Origin: *` と credentials の併用、Origin をそのまま反射、正規表現の `.` 未エスケープ
- セキュリティヘッダの削除・緩和（CSP、`X-Frame-Options`）
- WebSocket のオリジン検証
- キャッシュ: 個人情報を含むレスポンスの `Cache-Control`、キャッシュキーに認証情報が含まれていない（キャッシュポイズニング・他人の応答）
- レート制限・リソース制限のない高コスト操作（検索、エクスポート、メール送信、SMS）

## 依存関係とサプライチェーン

- 追加・更新された依存に既知の脆弱性がないか（lockfile の差分を見て、`npm audit` / `pip-audit` / `govulncheck` / `cargo audit` が使えれば回す）
- 依存のピン留めが外れた、取得元が変わった、ポストインストールスクリプトが追加された
- 新しく外部に送るデータ（テレメトリ、エラーレポート）

## 判定のしかた

候補が立ったら反証の手順で確かめる。セキュリティに固有の反証ポイント:

- その入力は本当に攻撃者が制御できるか（認証済みユーザーだけか、管理者だけか、内部サービスだけか）。制御できる主体が限定的なら severity を下げる。ただし「認証済みユーザーが他人のデータを読める」は high 以上
- 途中の層（ミドルウェア、バリデータ、ORM、フレームワークの自動エスケープ）で防がれていないか **実際に読んで** 確認する。推測で「フレームワークが守っているはず」としない。守っているなら、どの行がそうしているかを根拠に書く
- 到達経路を **番号付きの再現手順**（防御側が追試するためのもの。必要最小限にとどめる）として書けるか。書けたら `confirmed` または `likely`。書けないなら `possible` で、high 以上のときだけ報告する
- CWE 番号を付けられるなら付ける（読者が分類・追跡しやすい）

**同時に見ること**: セキュリティ修正の PR では、修正が **全箇所** に当たっているか（同じパターンが他のファイルに残っていないか grep する）と、修正自体が新たなバグを入れていないか（バリデーションが正当な入力を落とす、エスケープの二重適用）を確認する。
